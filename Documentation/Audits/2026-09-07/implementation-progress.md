### Sidebar identity review

Apple's [ForEach documentation](https://developer.apple.com/documentation/swiftui/foreach) and [Demystify SwiftUI performance](https://developer.apple.com/videos/play/wwdc2023/10160/) confirm that stable, inexpensive row identifiers support incremental collection updates. `ForEach(items)` already uses `Identifiable.id`; writing `ForEach(items, id: \.id)` supplies the same identity. This differs from the [`.id(_:)` view modifier](https://developer.apple.com/documentation/swiftui/view/id(_:)), whose value defines a view's identity and resets its state when changed. Stable identity preserves lifetime but does not prevent dependency-driven body evaluation or layout.

The shared saved/current rows, nested folders, split-group members, and essentials already use model-backed identifiers. `BrowserSidebarFolderListItem.id` and `BrowserSidebarTabListItem.id` wrap the existing folder, tab, or split-group ID, independent of title, selection, loading status, and collection position. Reconstructing the folder projection preserves these IDs. Row `.id(tab.id)` modifiers also provide the scroll targets used by mobile page promotion. Space roots use the Space/profile runtime assignment to reset content when that assignment changes; the mobile pager additionally exposes the Space ID as its scroll target. These boundaries remain intentional.

No missing stable identifier was found in these collection paths, so this review adds no app-code changes or tests. The sidebar uses native scroll views with SwiftUI stacks rather than `List`; its inner saved/current groups are largely eager. Identity is therefore already in place, while row construction, layout, and interaction work remain the measured optimization direction. This source review is not an additional performance capture.
