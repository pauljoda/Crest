# Space switching: source audit and implementation direction

Reviewed at `457ac1d2`. This report covers the shared pager and macOS presentation/runtime path, alongside the [SwiftUI performance audit](swiftui-performance.md). It describes source-supported work and proposed implementation targets, not measured latency or a completed optimization. See [measurements.md](measurements.md) for the isolated Release baseline and its limits, and [validation.md](validation.md) for checks actually executed. No production changes are included.

## Recommendation

Make Space switching the first implementation milestone. **A horizontal trackpad gesture or horizontal wheel burst should request one adjacent Space, then play a fixed, cancellable transition.** Replace the freely scrolling horizontal Space strip and its snap/recenter feedback with this discrete intent. Removing the actual horizontal `ScrollView`/`LazyHStack` is the preferred implementation direction; the vertical tab-list scroll views remain unchanged.

Prepare adjacent Spaces through inexpensive chrome projections and already-resident content. Crest already retains previously visited WebKit pages. A lightweight selection still initiates global session publication, whole-library projections, runtime reconciliation, and eager row work as motion starts. Remove avoidable work while introducing the explicit gesture contract, before allocating additional WebKit runtimes.

One shared transition owner coordinates the requested/presented assignment, fixed animation, and restrained background color wipe. Raw scroll distance and momentum never drive the visual offset or additional selections. Keep the live page host's layout stable and animation independent of network completion.

### Existing input handling and the replacement seam

The current [pager at lines 34–57](../../../CrestShared/Features/Chrome/Components/BrowserSpacePager/BrowserSpacePager.swift#L34) uses a horizontal `ScrollView`, `LazyHStack`, `.viewAligned(limitBehavior: .alwaysByOne)`, and `scrollPosition`. Selection follows `visibleSpaceID` changes at line 89; recenter/settlement logic then coordinates the scroll position. One-page snap configuration is already present. It does not implement a separate “one accepted gesture → one Space request” contract. [The Mac horizontal-scroller observer](../../../CrestMac/Features/Chrome/Components/BrowserPlatformHorizontalScrollerSuppressor/Components/BrowserPlatformHorizontalScrollerObserverView.swift#L3) hides the backing scroller; it does not segment gestures.

There is a useful local event-adapter example in the **vertical widget deck**, not the Space pager: [BrowserSidebarLoadedContent.swift:185](../../../CrestMac/Features/Sidebar/BrowserSidebar/Components/BrowserSidebarLoadedContent/BrowserSidebarLoadedContent.swift#L185) models delta, timestamp, precise/phase/momentum hints; [its observer at line 330](../../../CrestMac/Features/Sidebar/BrowserSidebar/Components/BrowserSidebarLoadedContent/BrowserSidebarLoadedContent.swift#L330) scopes events to its window/region. Its precise accumulator can rearm a latch after elapsed time since a flip, and its discrete-wheel path rate-limits repeated flips. Reuse the thin adapter pattern, not those repetition rules or its numeric constants, for strict one-Space-per-gesture behavior. Leave the widget deck's vertical behavior alone.

Apple documents that legacy wheel and momentum events may have no ordinary [gesture phase](https://developer.apple.com/documentation/appkit/nsevent/phase-swift.property); [momentumPhase](https://developer.apple.com/documentation/appkit/nsevent/momentumphase) identifies momentum separately. Normalize phase and units at the platform boundary instead of assuming every precise stream delivers `.began`/`.ended`.

The shared [swipe modifier](../../../CrestShared/Features/Chrome/Components/BrowserSpaceSwipeModifier/BrowserSpaceSwipeModifier.swift#L3) already emits an intent on drag end, but its mobile toolbar consumer pages split cards. Do not repurpose that consumer as Space switching. Share relevant direction/layout policy, while the sidebar's touch adapter requests the same discrete Space transition as the Mac sidebar.

[BrowserPagePool+SpaceSelection.swift:4](../../../CrestMac/Infrastructure/WebKit/BrowserPagePool+SpaceSelection.swift#L4) resolves the selected split group. If any non-Start-Page member is not resident, it intentionally presents a Start Page and deactivates content (lines 10–20). **Highest-value source conclusion:** selection-only work is not yet distinct from membership/content changes. That is a concrete optimization seam, even with resident pages and warm chrome. ## Ordered implementation plan

### 1. Establish a narrow selection transaction

Create a shared selection/structure change description so a pure Space switch carries old/new Space assignment and selected card IDs without pretending all tabs, icons, permissions, or content-blocking policies changed. Have the store continue to own durable selection, but route window-local selection through its narrow persistence/publication path. Preserve cross-window data semantics: other windows should not rebuild all session objects merely to retain the selection they already own.

Split runtime observation into membership/content revision and selection revision. A selection-only change should update active extension tab/window state and presented card state once. It should not rebuild tab-icon/content-blocking projections, prune archived state, repair unchanged tab groups, or reapply unchanged credential access to every runtime. Structural mutations, lock changes, profile replacements, tab moves, and permission changes still run the appropriate reconciliations. Coordinate the extension-state delta with the [extension audit](extensions.md) rather than suppressing required activation events.

Apply the [concrete sidebar changes](swiftui-performance.md) in the same performance milestone: hoist insertion maps once per section, cache row/folder presentation by structural inputs, and remove each row’s direct dependency on the entire session for its read-only availability display. Keep live action authorization/assignment checks.

**Acceptance:** one presentation transaction and one necessary extension selection update per committed switch, including all required split-card events; zero unrelated icon/permission/structural rebuilds for a warm A→B switch; no resident WebKit page creation or initial navigation for unchanged resident groups.

### 2. Recognize one Space intent and own its fixed transition

Use one small shared intent policy and one thin Mac event adapter, alongside a per-window transition owner. The adapter converts `NSEvent` horizontal/vertical deltas, timestamp, precision, `phase`, and `momentumPhase` into normalized input. It owns event delivery and monitor lifetime, not Space selection or animation. The shared policy owns axis recognition, bounded accumulation, and the accepted-gesture latch. A touch recognizer can feed the same discrete direction without emulating wheel phases. Do not introduce a general gesture framework.

Scope recognition to the sidebar window/region at gesture start; once claimed, finish that gesture consistently even if the pointer moves. Process zero-delta terminal events before delta/dominance filters. Initially unclaimed or vertically dominant events continue to the existing vertical tab scroller; a vertical gesture remains vertical until its boundary. Consume only the claimed horizontal sequence and its momentum so it cannot also drive another horizontal control. Tab/folder dragging locks Space recognition and clears any uncommitted candidate. Use native adjusted delta direction once, then the shared layout-direction policy; do not invert natural scrolling twice.

| Input state or event | Required result |
|---|---|
| Precise `.began` / first valid changed event | Begin an undecided gesture; ignore `.mayBegin` as a selection trigger. Accumulate deliberate movement before locking an axis. |
| Horizontal threshold crossed | Emit one adjacent-Space request and latch. Clamp/discard remaining accumulated distance; a large delta cannot emit multiple steps. |
| Reversal abandoning the candidate before acceptance | Cancel the candidate with zero commits; do not issue a compensating selection. Calibrate jitter tolerance with actual event streams. |
| Direction reversal or more deltas after acceptance | Keep the latch: one accepted gesture stays one step, even if animation has already completed. |
| `.ended` / `.cancelled`, followed by momentum | Close/cancel recognition but suppress its momentum tail; momentum never initiates or queues another step. A fresh non-momentum `.began` can establish a new gesture. |
| Precise events without phases; ordinary nonprecise wheel bursts | Use a bounded signed accumulator and inactivity boundary measured from the **last event**, with separate unit normalization. Emit at most one step per burst. Do not rearm merely because a fixed time elapsed since the accepted step, and do not debounce every delta into an independent action. |
| Focus/window loss, Space removal, access change, drag lock | Reset recognition and invalidate dependent pending work; never strand a latch or commit against an obsolete assignment. |

For phase-less streams, no missing event can reliably identify a physical finger lift. An idle boundary is the explicit fallback, not proof of a new gesture. Tune threshold, dominance, wheel normalization, and idle interval using trackpad, Magic Mouse, and ordinary-wheel traces; the existing 30/72-point thresholds and 0.3-second widget gap are not validated Space-switch constants. A long continuous phase-less stream must not repeatedly step without a quiet boundary. Vertical wheel scrolling must remain vertical.

The per-window transition owner stores requested target, actually presented assignment, direction, fixed-animation phase/progress, and generation. Recognized previous/next intent resolves **one** neighbor through shared Space-order/access policy with explicit boundary behavior. Preserve nonwrapping gesture/accessibility ends; [accessibility currently clamps](../../../CrestShared/Features/Chrome/Support/BrowserChromeAccessibility.swift#L15), while [keyboard adjacency currently wraps](../../../CrestShared/Application/BrowserStore/BrowserStore+TabOrganization.swift#L707). Carry that existing distinction into the request policy until intentionally unified; do not silently change it during the animation refactor. It starts one predetermined animation after recognition, independent of remaining gesture deltas. Pager replacement, keyboard, picker, any Space slider, auxiliary buttons, accessibility adjustable increment/decrement, and named Previous/Next Space actions all enter this owner. Direct indexed/picker targets remain explicit target requests.

Keep at most one active transition and one pending adjacent step. A distinct new gesture during motion may fill that pending slot; later gestures coalesce to the latest direction instead of accumulating an unbounded queue. Resolve the pending neighbor from the committed destination when it runs. A direct target request supersedes the pending step and invalidates stale target preparation. Expose/trace accepted, coalesced, and completed intent distinctly; coalescing must not silently become multi-Space traversal from one wheel stream.

Commit durable selection and the resident presentation once at the coherent handoff, acknowledging input immediately. Keep a valid outgoing host or transition surface until the incoming resident host is ready; do not wait for network or for the fixed animation to finish. Commands, focus, and hit testing agree with the actually presented assignment. Each readiness/animation completion carries the generation and Space/profile assignment: rapid A→B→C→A cannot let a stale earlier A completion win. Relock, deletion, profile replacement, window closure, and Reduce Motion cancel/settle this owner. Animation completion does not release the input gesture latch.

**Why not just flip the existing flags:** [BrowserSpaceContentSelectionPolicy.swift:1](../../../CrestShared/Features/Sidebar/Support/BrowserSpaceContentSelectionPolicy.swift#L1) disables both deferred-selection flags because the former approach left selected tab and active page out of sync, exposing the unloaded-tab fallback. Explicit requested/presented state must preserve immediate resident-content behavior and intentional unloaded Start Page entry when replacing the scroll mechanism.

### 3. Prepare a bounded adjacent-chrome window

Maintain immutable prepared sidebar data for current/previous/next Space keyed by `(spaceID, profileID, tab/folder structure revision, branding revision, access state, capability class)`. Resolve tab sections, flattened visible folder order, following-ID maps, motion IDs, and branding inputs once when those inputs change. Prepare missing neighbor projections after the current interaction settles; cancel obsolete work when the adjacency window changes. The immediate selection should consume a ready value, not rederive the full section.

Replace the horizontal strip with a clipped fixed container, such as a `ZStack` holding only outgoing/incoming sidebar panels during motion. Key panels by Space/profile assignment, not by transient slot index. Preserve visited vertical scroll anchors and relevant presentation state in a small Space-keyed owner when a panel leaves the bounded live set. The transition no longer needs a horizontally scrolling `ForEach` over every Space or scroll-position feedback that repeatedly publishes selection. Keep vertical tab scrolling native. Make rows lazy only where measured and preserve selected/promoting/dragged source geometry; do not retain three eager 500-tab trees simply to claim prewarming.

For WebKit, begin by reusing existing resident pages. If the trace shows attach/raster readiness dominates after data-path improvements, experiment with a bounded host surface for the outgoing and incoming already-resident selected group. A `WKWebView` can have only one parent: do not mount the same page simultaneously in two SwiftUI hosts or recreate it to animate. Avoid resizing a live WebKit viewport as a side effect of a wipe.

Any **new** speculative page loading should be a separate residency-policy change, not a side effect of chrome prewarming. Default excludes locked/private Spaces, explicitly unloaded tabs, profile replacement, and deletion. Preserve existing audio/capture/PiP behavior; preload must not activate/focus the tab, request credentials, auto-unlock, or announce it as visible. Limit concurrent preparation and account for all split members, app plus WebContent memory, power, and network usage. Existing pressure handling must be able to drop warmed resources immediately. No evidence yet justifies paying this cost for smooth warm switches.

### 4. Tie the color wipe to the fixed transition

The root backdrop currently reads `browser.selectedSpace` directly ([BrowserRootShell.swift:21](../../../CrestMac/Features/Browser/BrowserRootView/Components/BrowserRootShell.swift#L21)). [BrowserRootBackdrop.swift:21](../../../CrestMac/Features/Browser/BrowserRootView/Components/Backdrop/BrowserRootBackdrop.swift#L21) animates material/base opacity based on transparency/focus; it does not define a Space-branding transition. [BrowserWindowAtmosphere.swift:10](../../../CrestShared/Features/Browser/Components/Backdrop/BrowserWindowAtmosphere.swift#L10) therefore receives the new branding while the sidebar follows its own native settling animation.

Use two stable branding render inputs—outgoing and incoming—and animate only a clipped reveal or crossfade with the owner’s fixed animation progress/direction. This progress is time-driven after the accepted intent, not bound to scrolling deltas or momentum. Keep window material a stable layer, avoid duplicating live WebKit or widget-deck trees, and do not rebuild all gradient/texture geometry each animation frame. Limit the wipe to the chrome/background region, behind readable content. Update foreground contrast coherently with whichever branding is visible.

Texture is a conditional cost to profile: [BrowserSpaceThemeTexture.swift:5](../../../CrestShared/Features/Spaces/Components/BrowserSpaceBranding/Components/Banner/BrowserSpaceThemeTexture.swift#L5) draws asynchronously but constructs up to 20,000 grain particles per render callback. If the trace identifies repeated texture render cost during the wipe, use a size/scale-keyed static noise tile or cached paths. The source alone does not prove the Canvas redraws on every frame, so this is not the first assumed bottleneck.

Reduce Motion: immediate coherent handoff without spatial motion; preserve the one-step input latch even though the visual transition finishes immediately. Reduce Transparency: preserve the existing opaque/readability treatment instead of adding more material blending. Increase Contrast: evaluate both endpoint themes and the intermediate mask edge.

**Proposed budgets, not current measurements:** at 120 Hz a frame is 8.33 ms; at 60 Hz it is 16.67 ms. Target a lightweight input acknowledgment within the next displayed frame, Crest-owned synchronous input work ≤2 ms, and warm-switch main-thread update work below roughly 4 ms at 120 Hz / 8 ms at 60 Hz, leaving time for system/render work. Require no missed-frame hitch in a fixed warmed repeat-switch sequence and report p95/p99 update/attach duration plus memory delta. These are engineering targets to validate on representative hardware, not universal SwiftUI guarantees. Keep cold network completion out of the animation’s critical path. The existing 0.32-second snap duration is only a comparison point when tuning the proposed fixed transition; it is not a requirement to retain snapping or that duration. Measure recognition-to-first-frame separately from total animation duration. A shorter animation alone does not address a dropped frame.

Use temporary event logging and physical-device traces for long flicks, momentum, unphased streams, slow diagonals, natural-scroll direction, separate rapid gestures, and pointer movement outside the initial region. Record raw normalized input, accepted intent, presentation generation, and displayed frames without page content. Synthetic wheel events alone cannot certify hardware segmentation or native feel. Remove diagnostic probes after the implementation is validated, following [test-retention.md](test-retention.md).
