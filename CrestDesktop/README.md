# Crest for Windows and Linux

Crest's Windows and Linux app draws its interface inside Crest's own
Chromium, as Chrome, Edge and Vivaldi do, so pages and chrome share one
compositor: page cards clip to their corners, Peek and notices sit over pages,
and nothing waits on another toolkit's window. The interface is TypeScript and
React; the core is the same NativeAOT `CrestCore.Native` every Crest app
links, and the engine is Crest's Chromium fork built for the host.

```text
crest.exe — Crest's Chromium browser process
├─ CrestCore.Native.dll   the core: state, rules, storage (C ABI)
├─ Chromium binding       CrestEngines/Chromium/Overlay/.../crest_engine_*
├─ Desktop shell          windows, page layers, the bridge to the core (engine input)
└─ Interface bundle       CrestDesktop/ui, loaded from the app folder (not an engine input)
```

## Layout

| Folder | What it holds |
| --- | --- |
| `ui/packages/contracts` | The contract models and wire codec, generated by `CrestCore.Generator` (`contracts.generated.ts`), and the wire runtime (`wire.ts`). |
| `ui/packages/core-client` | The interface's path to the core: the transport, `CrestCore` (intents, queries, engines) and the read model the changes keep. |
| `ui/packages/design` | Crest's design tokens, the values `CrestShared/DesignSystem/Tokens` names. |
| `ui/app` | The browser window. |
| `devhost` | A development bridge: the native core in a local process, reached over a WebSocket. |

The interface reaches the core only through the contract: it encodes intents
and queries and decodes changes and answers with the generated codec, and a
bridge carries the bytes. In the product the shell's bridge carries them as
WebUI messages; in development `devhost` carries them over a WebSocket, so the interface
runs in any browser against the real core, with frames standing in for an
engine.

## Develop the interface

Publish the core for this machine, start the bridge, then the interface:

```sh
dotnet publish CrestCore/src/CrestCore.Native -c Release -r win-x64 -o <core output>
dotnet run --project CrestDesktop/devhost -- --core <core output>/CrestCore.Native.dll
npm install --prefix CrestDesktop/ui
npm run dev --prefix CrestDesktop/ui
```

Open `http://127.0.0.1:5173`. A frame shows only sites that allow being
framed; the engine contract, page lifecycle and every core rule are the real
ones.

After changing a contract record, run `Scripts/control-plane/generate-contracts.sh`
(or `dotnet run --project CrestCore/tools/CrestCore.Generator`), which writes the
TypeScript models beside the Swift and C++ ones.

## Windows build requirements

- Visual Studio 2026 with Desktop development with C++, MFC/ATL and the
  Windows 11 SDK 10.0.28000 with its Debugging Tools (Chromium pins that SDK).
- .NET SDK pinned by `CrestCore/global.json`, Rust through rustup (the content
  filter), Python 3.11 or newer, Node.js and Git for Windows (which carries GNU
  patch).
- Keep the Chromium tree at a short path such as `C:\CrestBuild\cr\src`:
  Windows limits paths to 260 characters unless long paths are enabled.

NativeAOT finds the linker through `vswhere.exe`; put
`%ProgramFiles(x86)%\Microsoft Visual Studio\Installer` on `PATH` before
publishing the core.

## Prepare and build the Windows engine

The Windows host's toolchains, the Git dependencies a Linux-exported source
archive lacks, and its build arguments are in
`CrestEngines/Chromium/Hosts/win-x64.json`. The scripts pick the host from the
machine they run on:

```sh
py -3 Scripts/control-plane/prepare-chromium.py --source C:\CrestBuild\cr\src --downloads C:\CrestBuild\downloads
py -3 Scripts/control-plane/apply-chromium-host.py --source C:\CrestBuild\cr\src --apply
py -3 Scripts/control-plane/configure-chromium.py --source C:\CrestBuild\cr\src --configuration development
py -3 Scripts/control-plane/build-chromium-baseline.py --source C:\CrestBuild\cr\src --jobs 16
```

## Run Crest in its Windows engine

The shell (`CrestEngines/Chromium/Overlay/chrome/browser/ui/crest/crest_desktop_*`
and `desktop-host.patch`) starts when Chromium is launched with
`--crest-control-plane`. It loads `CrestCore.Native.dll` and the interface's
built files from beside `chrome.exe`, or from the paths `--crest-core` and
`--crest-interface` name, and opens a Crest window whose interface is
`chrome://crest-desktop`. Launch it with a profile directory of its own:

```sh
npm run build --prefix CrestDesktop/ui
C:\CrestBuild\cr\src\out\CrestBaseline\chrome.exe --crest-control-plane --user-data-dir=C:\CrestBuild\profile --crest-core=<core output>\CrestCore.Native.dll --crest-interface=CrestDesktop\ui\app\dist
```

Inside the engine the interface talks to the core through the shell's WebUI
bridge rather than `devhost`, Chromium's binding is the engine, and each page
card holds the page's own surface as an `<embed>`. Ctrl+Shift+F12 inspects the
interface; F12 is the page's inspector, as in other Windows browsers.
The session lives in the profile directory's `Crest` folder; a profile with
none starts the session a first install starts with.

## The window

The title bar is the interface's. The system keeps the window's border,
shadow, rounded corners, snapping and resizing; the interface marks where the
window moves with `-webkit-app-region: drag`, and draws the minimize, maximize
and close buttons at the top right, as every Windows window has them, from the
state the shell reports (`crestWindowState`). Chromium adds each box's drag
area in document order, later boxes over earlier ones, children taking their
parent's, and never clips them to scrolling. So a layer laid over the whole
window takes `-webkit-app-region: initial`, which keeps it out, and marks only
what can be pressed in it `no-drag`; and the title bar is the window's last
element, so content scrolled up beneath it cannot take back its drag area.

Every Crest window is a saved window. A launch's first window asks the core
which windows the last launch left open (`LaunchWindows`), becomes the
frontmost of them and has the shell reopen the rest. However a window is asked
to close (its button, Alt+F4, the taskbar), the shell asks the interface first
(`crestCloseRequested`). The interface lets the window's pages go
(`ReleasePage`), as a closing Mac window does, since a page the engine closed
by itself would close its tab; then the last window remembers every window for
the next launch (`RememberWindowsForLaunch`) and any other closes for good
(`CloseWindow`). A window whose interface does not answer closes after two
seconds anyway.

What a page asks of the person comes from the core, which keeps it until it
is settled (`ScriptDialogAsked`, `AuthenticationAsked`, `PermissionAsked`,
then `PromptSettled`). Script dialogs and a server's sign-in are sheets over
the page card, which hold the page until answered; a permission request opens
below the address field, as the Mac's does from its site control. Each answer
goes back as the matching `Answer…` intent.

Site Controls open from the address field's trailing button, as the Mac's do
(`app/src/shell/SiteControl.tsx`): the page's title and host; Copy Link,
Reload and Inspect; how its connection is secured; the permissions its site
has in the Space, each the core's answer (`SiteDecision`) and each set as the
person picks it from a menu (`DecideSitePermission`); and Clear Cookies and
Clear Cache, which the core erases through the engine (`DeleteSiteData`,
answered by `DataDeleted`) before the page reloads. The lock in the field's
leading slot, and the panel's Certificate, show the chain the engine verified
the page with (`PageCertificates`) in the system's own certificate dialog,
which the shell opens (`certificate`). Where the page's Space blocks ads and
trackers, Block Ads and Trackers turns blocking off for the site, or on
again, and reloads the page (`SetSiteContentBlocking`), as the Mac's page
action does; Windows browsers keep a site's tracking prevention there. The Mac's region capture, developer
mode, extension controls and Open in Space wait for those features here.

A pop-up a page's engine blocked turns Site Controls to the warning tone and
heads the panel with the Mac's notice (`app/src/shell/blocked-popups.ts`): the
engine reports it (`PopupBlocked`), and the core's notice rules
(`BlockedPopupTransition`) decide what the page shows, once per document.
Each committed page, and every page when a Space's choices change, applies its
site's automatic pop-up choice to its engine (`SetSitePermission`); Allow
Automatic Pop-ups saves the choice and opens what the engine held
(`ShowBlockedPopups`).

Spaces follow the Mac's sidebar (`app/src/spaces`). The switcher under the
tab list is the Mac's compact strip: the sidebar toggle and the lists button
32 points square at either edge, and centred between them a track of the
Spaces' crests, fitted to the room in steps of 5% down to 30% before it
scrolls behind its arrows. The track is a well recessed into the sidebar,
with a white selector and a softer white highlight across the group of
Spaces that share a profile, each as strong as the picker's tone over the
Space's sidebar gives it. Each Space draws its
identity as the Mac does: the crest composed from its look's plate, field,
band, trim and charge (the heraldic and simple charges are the Mac's own
drawings), or its symbol or emoji, with the lock on a Space that asks for
authentication. A Space's look is a Background and an Accent, each one color
or a gradient of up to three (`app/src/spaces/space-fills.tsx`): the sidebar
wears the Background, the crest's layers and the icon the colors they draw
from, each running into its own gradient, blended as the Mac's perceptual
gradients are, through the hues between rather than through gray, and the
sidebar's text reads over the colors it paints. The
header above the tabs opens and closes the saved tabs (`ExpandSavedTabs`) and
offers the Space's actions; the empty area's menu adds New Space…
(`CreateSpace`) and New Sub-Space (`AddSubSpace`). A Space's name, search,
archiving and what it keeps are edited on its page in Settings; locking,
reordering, deleting and its appearance wait for those parts of Settings.

One pager moves every part of a Space change on one clock, as the Mac's
`SpacePagerViewport` does (`space-pager.ts`): the sidebar's Space pages slide
a whole sidebar width a Space, the switcher's selection travels between the
crests, and each Space's banner fades in over the last. Every change slides
one page, on the Mac's curve (cubic-bezier 0.27, 1, 0.18, 1, 0.28 seconds a
page): between neighbours, around the ends for Next or Previous Space, and to
a Space further away along a strip that puts it next door. A horizontal swipe
on a precision touchpad follows the touchpad's own phases, which the page's
wheel events leave out and the shell sends beside them (`crestWheel`, once
`hello` says `wheelPhases`): the strip tracks the fingers point for point from
the moment the swipe begins, holds still while they rest, and lets go only
when they lift, plainly or into the system's momentum, which never moves the
strip itself. Released past halfway, or thrown there by the fingers' speed
over their last 80 ms, it settles on the next Space, else back, carrying on
from that speed on a critically damped spring; only then does it ask the core
to show the Space (`ShowSpace`). Without phases, as in a development window, a
swipe ends when its input goes quiet. A wheel's horizontal notches step a
Space at a time. A drag in flight holds the strip still. While the strip
moves, its pages and the Spaces' banners stay on compositor layers of their
own, so each frame only moves them. A settle runs on the compositor: each
page, card and banner hands its course along the settle to a Web Animation,
sampled at the display's rate, so a slide repaints nothing on the way, which
an integrated GPU on a large window can't keep up with. Every leaf's
animation starts on one clock, at the settle's first frame rather than when it
was asked for, so a slide never opens past the frames the window spent
drawing it; the switcher's selection, which still draws each frame, keeps a
layer of its own so it repaints only itself.

The page area moves with the same pager (`SpaceContentStrip.tsx`), as the
Mac's content pager does: each Space's card stands in a page as wide as the
content area, inset included, and slides a page a Space with the sidebar. The
Space a slide leaves or reaches shows its card as a still preview: the page
its shown tab holds, or the Start Page the window would show there.
Neighbouring Spaces of a group that show the same pinned tab share a place, so
moving between them moves no card. With page sliding turned off
(`crest.appearance.animate-space-pages`) or Reduce Motion on, cards keep their
place and fade, the card left behind whole until halfway. An embedded page
draws only the part of itself it saw on screen when it last laid out, and a
card moves by transform, without laying out; so a card coming on screen first
lays its page out in place, unseen beneath the others, and each page's
surface is kept so a card embeds a page it has shown before at once. Drawn in
place on a layer of its own, the card is rasterized there too, so a slide from
rest waits at its start for it (at most 300 ms) instead of rasterizing it in
its first frames; a swipe's release never waits, carrying on from the
fingers. An embedded page keeps its surface while its card moves: Crest's
Chromium tells the page only where its embed now stands, under its current
`viz::LocalSurfaceId`, keeping its size through the pixel it gains and loses
as the move snaps to pixels, and the part of it that showed as it passes the
area's clip (`desktop-host.patch`, in `components/surface_embed/renderer`).
Upstream makes a new surface, and resizes the page, for every move, and the
window then waits each frame for the page's own renderer to draw for it,
which made a slide over a live page drop a frame in three.

Chromium lets go of what a hidden page has drawn, so a page coming back from
a Space that wasn't shown would draw itself again as it slid in, more than
an integrated GPU fits between a slide's frames. The Mac's engine keeps
drawing the page through the swipe; here the pages the window shows are
pictured whole, at the screen's own pixels, just before the window asks the
core for another Space (`page-stills.ts`): the core hides the pages it
leaves, and a hidden page draws no frame to picture. The card that brings a
page back slides in as its picture over its embed, which stands unseen, so
the page stays hidden; once the strip lands the page wakes in that same
embedding beneath its picture, which fades once the page has drawn, as a
picture of one pixel the engine takes from the page's next frame says. A
card without a picture of its size, as after the window or the sidebar
changed size, shows its live page instead, as before. A page coming back on
screen allocates a surface id of its own as it reconnects, under the
embedding it last had; upstream surface embedding merges that id into the
new embedding, whose ids then run a child sequence number ahead of the
page's: from the page's next resize the window named surfaces the page never
drew, waiting out each one's deadline, and no picture of the page ever came.
Crest's Chromium merges only an id of the current embedding
(`desktop-host.patch`). It also encodes a page's picture beside the
browser's thread, which routes a swipe's input (`crest_engine_page.cc`). The
window keeps its latest six pictures, in memory only.
The band of pinned tabs a group shares does not hold still in the sidebar yet.

A Space's cards are the core's (`WindowState.cards`): a Split View's members
side by side, or the shown tab alone, which is a one-card row
(`PageColumns.tsx`), as on the Mac. Each card opens and loads its own tab's
page. Columns share the row by the window's stored shares
(`splitColumnShares`) once the 8-pixel gaps are paid for, none narrower than
240 pixels, and a row too narrow clips. A divider in each gap tracks the
pointer and keeps its shares on release (`ResizeSplitColumns`); arrow keys
step it 24 pixels. A press in a card, or its page taking the keys, makes it
the card the chrome speaks for (`ShowTab`), as does the pointer arriving on it
where focus follows the pointer; it wears the Space's colour while there are
several. Joining and leaving settle with the row's motion, and showing
another tab alone lands at once. The sidebar's menus split, step and separate
cards, and the palette offers the split commands.

A link the core opens in Peek (`PeekRequested`, Alt-click by default) opens a
transient page (`OpenPage` with `TransientPresentation.peek`) that loads the
link its source page staged (`StageLink`), in a card over the dimmed page
area that grows out of the middle and goes back into it. Esc, Close Tab, the
close button or a click outside close it and let its page go (`ReleasePage`);
Open In… keeps it as a tab of its Space or another (`PromoteTransientPage`),
which takes the live page where the core says it can (`MovePage`). The
engine doesn't say where on the page the link was, so the card grows from the
middle.

Holding Most Recent Tab's keys (Ctrl+Tab, Ctrl+Shift+Tab backward) shows the
recent-tab switcher (`app/src/switcher`): the window's recent tabs
(`RecentTabs`), pictured by their engines as they show (`CapturePage`), with
the highlight moved by each press, the arrows and the digits, and letting the
keys go shows the highlighted tab; a quick press goes straight to the tab
before. Chromium drops the key-ups that follow a key-down the browser takes
from a document, so these keys reach the interface, or a page, before the
shell (`yieldsToText`): the window hears them itself where it has the
keyboard, and the shell runs the command where a page lets them go. A page
that handles Ctrl+Tab itself keeps it.

The sidebar's Common Lists button opens the Space's Archive, History or
Downloads in place of its tabs, as the Mac's does (`app/src/utilities`): the
list chosen for the Space from the button's menu, Archive at first, or
Downloads while downloads finished unseen, which the button's badge counts.
Opening a list fans its three destinations out beside the sidebar to switch
between, and puts a search field and a filter menu where the address field
stood. Each list comes from the read model (`ArchiveChanged`,
`HistoryChanged`), searched and filtered on the spot and grouped by when:
History is the Space's group's. An archived tab restores into the Space's open
tabs (`RestoreArchivedTab`); a history entry opens in a new tab
(`OpenTab`); the History filter menu clears the group's history after asking
(`ClearHistory`). Show Archive, Show History (Ctrl+Y) and Show Downloads open
or close their lists; a click on the page or the list's blank space puts it
away.

Downloads are the core's records (`DownloadUpdated`, `DownloadsRemoved`),
listed in the sidebar's Downloads list. The interface answers where
each file goes, as the Mac's download prompts do: it asks the shell
(`downloadDestination`), which picks the Downloads folder under a name no file
there has, or shows the system's Save dialog when the engine asks for one; the
first window to ask claims the question. A download the core judges risky asks
the person in the window in use (`DownloadApprovalAsked`). Finished files open,
and show in Explorer, through the shell.

Each window's interface keeps its own read model, which only changes update,
where the Mac's windows share one. A window that opens after others asks the
core what it missed (`CatchUp`): the engines and the shortcuts they offer, the
search catalog, every download, then the questions still waiting, as changes
it applies like any batch. The launch's first window restores the search
catalog for the person's language and region (`RestoreSearchCatalog`), as the
Mac's launch does before any window shows.

The command palette (`app/src/palette`) is the Mac's: Ctrl+T opens it for a
new tab, Ctrl+L and the sidebar's address field to edit the shown tab's
address, and the same keys put it away. The core ranks what it offers for each
keystroke (`PaletteSuggestions`), from the window's tabs, history, archive,
Spaces and the commands this window runs; an answer that arrives after a newer
keystroke is dropped, and Return, Tab or Down wait briefly for the answer to
what was typed. The interface keeps the field, the selection, the inline
completion and the provider or scope a person narrowed to, and performs each
row's activation, remembering the pick (`RecordPaletteChoice`). Ctrl+Return
opens an address in a tab behind, Ctrl+Shift+Return in a new tab, and
Shift+Return in Split View beside the shown tab; the Mac's Quick Window opening
waits for that feature here. Where the core allows search suggestions for
what was typed, it names the engine's suggestion address, and the shell
fetches it (`fetchText`) as the Mac does: without cookies or caching, giving
up after five seconds or past 64 KB (`app/src/palette/suggestions.ts`). Its
traffic annotation, `crest_search_suggestions`, is one the network's request
policy counts as the person's own, so it may reach Google; the filter lists'
may not.

The overlay palette grows out of the sidebar's address field and shrinks back
into it, on the Mac's BrowserCommandSurfaceMorph timeline
(`app/src/palette/palette-morph.ts`). Its glass grows from the field's frame
and corners to its own on the sidebar's morph spring, and takes over from the
field, which fades out and keeps its place, in the first 0.12 seconds. Its
contents keep their resting layout, ride with the frame's top edge, and show
through a clip that keeps the frame's true corners, fading in from 97% size
over the last 0.12 seconds of the frame's travel. Closing clears the contents
first, then the frame lands on the field as the glass hands back to it. With
the sidebar hidden the card comes and goes where it rests, and under Reduce
Motion at once. Every part moves on the compositor, the springs sampled into
CSS `linear()` easings (`springEasing` in `@crest/design`). Two things differ
from the Mac for the sake of an integrated GPU, which can't redraw a backdrop
blur in every frame while the scrim fades across the whole window. The glass
moves without its blur, and the resting glass, blur and all, fades in over it
once the frame settles. A Start Page's own palette also drops its blur while
the overlay is up: it only blurs the Space's smooth banner, mostly under the
overlay's card.

The sidebar's menus are Windows' own context menus, which the shell runs from
the interface's description (`menu`) as Chrome's run, so they reach past the
window and keep the system's keyboard and accessibility behavior. Their items
and wording are the Mac's (`app/src/shell/sidebar-menus.ts`). A folder's or
Split View's icon and color open the Mac's pickers in a popover
(`app/src/shell/pickers.tsx`). Tabs and folders rename in place, and a pinned tab, which has no room
for a field, in a dialog. Rows lift and drop as on the Mac
(`app/src/shell/sidebar-drag.ts`): the core says once where a lift may go
(`DropTargets`), each place the pointer reaches is checked (`CanSend`), and the
drop is one intent: between rows (`DropIntoList`), into a collapsed folder,
around a current tab as a new folder (`DropAroundTab`), or onto another Space
(`DropOnSpace`). An insertion line marks where it would land, as the Mac's
does without a measured gap, so nothing the pointer aims at moves.

The sidebar keeps a selection of its own, as the Mac's does, which the core
never sees (`app/src/shell/sidebar-selection.ts`). Ctrl-click adds or removes
a row, Shift-click selects the range from the last row clicked, and the rows
it holds wear their hover; a split selects as one, and a folder holds what is
inside it. Right-clicking a selected row offers the selection's menu, each
item asked of the core first; pulling one lifts them all, and the selection
follows them where they land. While the selection has the keyboard, Escape
lets it go, Ctrl+A selects every row, the arrow keys, Home and End move it
(Shift extends it), Enter opens a tab, Ctrl+C copies the addresses, Ctrl+D
duplicates, Ctrl+Backspace deletes and Ctrl+W archives it. The window asks the
selection before it runs a command from its keys, since the shell claims those
keys before the interface sees them. Ctrl+S
hides the sidebar or docks it again; while it
is hidden, resting the pointer on the window's leading edge brings it out as a
card over the page, which goes once the pointer leaves it for the page.
Hiding and docking move the page with the sidebar, as the Mac's page moves
in its morphs (`SidebarSlot.tsx`). The toggle slides the sidebar out or in
as a drawer, the page card's edge staying beside the sidebar's on every
frame, the page laid out at each width on the way. Hidden while the pointer
is on it, the sidebar turns into the floating card where it stands, its
shadow and backdrop fading in, the page growing beneath it, and the card
goes once the pointer leaves it. A card out over the page docks in the
Mac's two steps: the page moves aside beneath the card, then the card
settles into the column as its dressing goes. One spring, sampled each
frame, sets the sidebar's place and the page's edge together, so they never
part, and its last frame is where the presentation lays them out, so nothing
moves as the morph hands over. The cards' own layout animations stand aside
meanwhile (`cards-snap.ts`), since they would scale the live page from its
last box. While the morph runs, and while the sidebar's edge or a split's
divider is dragged, the page embeds carry `data-live-resize`
(`holdLiveResize` in `PageCard.tsx`), and Crest's Chromium draws each width
without waiting for the page to lay itself out at it (`desktop-host.patch`).
A page that lays out within a frame keeps up; a heavier one follows a few
frames behind, showing what it last drew, clipped by its card or with its
background beside it, instead of holding every frame of the motion. The mark
goes the frame after the morph hands over, or as the drag ends, and the page
catches up at its final width.

The sidebar's edge beside the page resizes it, docked or floating, between
the Mac's bounds (164 to 380, opening at 289), and its arrow keys step it.
Each window keeps its width and whether its sidebar is shown on this device,
as the Mac's window layouts do, in the interface's local storage
(`app/src/shell/sidebar-layout.ts`), and a window that keeps none opens at the
width last set. A page's surface takes the pointer's events whenever the
pointer is over it, even in the middle of a drag the interface began, so while
a resize or a lift holds the pointer the page card is covered
(`app/src/shell/pointer-hold.ts`), and the card follows the sidebar's width at
once.

What the page card shows is the core's answer for the shown tab
(`PresentPage`): the live page, a Start Page, or nothing yet while a tab whose
page went away restores itself. The Start Page (`app/src/shell/StartPage.tsx`)
is the Mac's: Crest's icon, the title in the Space's ink, the private browsing
notice in a private window, and the command palette in place, on the Space's
backdrop, which the card lets through. Its palette opens what it is given in
that tab (`NavigateTab`) and offers the window's commands only once something
is typed; New Tab on a Start Page gives it the keyboard again rather than
opening the overlay. The launch's frontmost window opens on a Start Page when
the core's launch plan says so (`LaunchPlan`), and entering a Space whose
shown tab has no page shows a Start Page there (`ShowStartPage`) rather than
loading the tab on the person's behalf, as the Mac's windows do.

A page has the keyboard while its `<embed>` is the interface's focused element.
When one of the interface's own elements takes focus, the embed gives the
interface the keyboard back (`desktop-host.patch` does this for surface
embeds), and when the palette goes the page takes it again.

A window's commands are the Mac's (`app/src/commands.ts`): each sends the core
the intent the Mac's sends, or asks the page's engine for view work.

Find in page and zoom are each page's, as the Mac's BrowserPage keeps them
(`app/src/shell/page-tools.ts`). Find floats the Mac's bar over the page's top
trailing corner (`FindBar.tsx`): typing searches (`FindInPage`), the engine
reports what it found as a presentation every window hears (`FindFinished`),
and the bar says "3 of 12", Return and Shift+Return step through the matches,
and Escape closes it and gives the page the keyboard back. Find Next and Find
Previous repeat the last query, bringing a closed bar back without taking the
keyboard, and leave their keys to the page while there is nothing to find
again. Zoom steps through the Mac's levels (`ZoomPage`) and says where it went. An address
leaves Crest only as the core's `LinkToCopy` answered it (Super Copy), and the
shell puts it on the clipboard (`copy`).

Keyboard shortcuts are the core's, as on the Mac: the core runs Windows as a
platform of its own (`DevicePlatform.windows`), whose defaults follow Windows
browsers where they differ from the Mac's, and publishes each command's keys
and page preference (`ShortcutsChanged`). Each window hands the shell the keys
of the commands it can run now (`shortcuts`), and the shell offers every key
down to them as the Mac's key monitor does: before a page, Prefer Crest runs
the command, Use Both runs it on a quick second press of keys the page kept
(the window says how, `crestPageKept`), and otherwise the page sees the key and
the command runs when the page lets it go. The interface's own fields see only
keys that edit text first. The interface runs the command (`crestShortcut`).

Settings is a tab of its own, as on the Mac (`app/src/settings`): Ctrl+, or
the palette's Settings pages show the Space's Settings tab, or open one
(`OpenTab` with `NativeView.settings`). Its sidebar lists the Mac's pages less
those only Apple's systems back, then the Spaces, each with its own Browsing
and Privacy page. A Settings tab keeps its page, a Space page's tab and each
page's scroll while it stays open. Each setting is the core's and changes
through the intent the Mac's sends. Shortcuts records keys in place: while it
records, the window binds none, and keys another command holds ask before
they move (`ShortcutInUse`, then `ReassignShortcut`). Privacy lists, for the
Space picked, what it keeps, the choices it saved for sites
(`SitePermissionsChanged`, which `AdoptSitePermissions` publishes), the sites
that keep data in it (`ReadWebsiteData`, answered by `WebsiteDataRead`), and
clearing what it browsed.

Ad Blocking is the Mac's pane (`app/src/settings/AdBlockingPane.tsx`): the
level, the catalog's lists by group, the person's own lists and filters, and
the sites with blocking off. As on the Mac, the platform downloads the lists:
each window's updater (`app/src/filter-lists.ts`) asks the core what is due
(`DueFilterDownloads`) when it starts, every hour, and whenever the lists or
Super Copy change, and the shell fetches each one (`fetchText`): https only,
without cookies, stored credentials or cache, following redirects only to
https, with the validators of the copy the core holds, and no larger than the
core keeps. Each outcome goes back to the core (`FilterDownloadFetched`,
`FilterDownloadNotModified`, `FilterDownloadFailed`, `FilterDownloadTooLarge`).

Extensions are Chromium's, as on the Mac, each Space's in its profile. A
Chrome Web Store listing's Add to Crest asks the shell (`StoreInstallRequested`),
and the window that showed it reviews the install (`InstallExtension`): the
package downloads (`ExtensionDownloadProgressed`), the core asks with what it
may access (`ExtensionInstallAsked`), and Add Extension, which waits half a
second, answers it (`AnswerExtensionInstall`), with copies in other Spaces if
chosen (`app/src/shell/prompts/ExtensionReview.tsx`). A Space's pinned
extensions sit above its tabs, and Site Controls lists every extension the
page offers, to run, pin or manage (`app/src/shell/ExtensionActions.tsx`,
`PinnedExtensions`, `PageExtensions`). A button runs its extension's action
for the shown page through the shell (`runExtension`), which opens the
extension's popup as Chrome's toolbar does, beside the button. Each Space's
Settings page lists its extensions, to turn on or off, remove, or copy to other
Spaces (`ListExtensions`, `ChangeExtension`). Side panels wait for that
feature here.

`chromium_engine.py key --host win-x64` names the Windows engine; its key
covers the inputs every engine shares and the Windows profile, so a change to
one host's inputs leaves the other's published engine valid.
